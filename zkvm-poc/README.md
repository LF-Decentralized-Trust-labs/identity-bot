# zkVM Proof of Concept — Verifiable Identity Confidence Score

This PoC demonstrates **verifiable local execution** of the Identity Agent's
confidence scoring algorithm using [RISC Zero's zkVM](https://risczero.com/).

It addresses [Issue #6](https://github.com/LF-Decentralized-Trust-labs/identity-bot/issues/6):
proving that a locally-computed identity score was generated by an unmodified,
known algorithm — without revealing the underlying credentials.

## The Problem

When the Identity Agent runs locally, a malicious user could modify the
scoring code to output a fake "100% confidence" regardless of actual credentials.
Peers cannot trust the score without verifying the execution.

## The Solution

The scoring algorithm runs inside a **Zero-Knowledge Virtual Machine (zkVM)**.
The zkVM produces a cryptographic receipt that proves:

1. **Which algorithm ran** — identified by its deterministic Image ID (hash)
2. **What it output** — the confidence score
3. **That it wasn't tampered with** — mathematically impossible to fake

The verifier never sees the private credentials — only the score and proof.

## Data Flow (Issue #6 Requirement)

```
KERI AID + Verified Credentials → Local Identity Agent zkVM
    → Confidence Score + ZK Proof → Verification by Peer (Alice)
```

1. **Rust** (1.77+):
   ```bash
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
   ```

2. **RISC Zero toolchain**:
   ```bash
   curl -L https://risczero.com/install | bash
   # Restart shell, then:
   rzup install
   ```

3. Verify installation:
   ```bash
   cargo risczero --version
   # Should output: cargo-risczero 3.0.6 (or later)
   ```

## Build & Run

```bash
cd zkvm-poc

# Build (first run downloads deps and compiles RISC-V guest — ~2 min)
cargo build

# Run the full prove + verify demo
cargo run
```

## Dummy Verified Credentials

The PoC feeds **two structured dummy VCs** into the zkVM (as required by Issue #6):

| VC | Type | Issuer | Age | Trusted | Revoked |
|----|------|--------|-----|---------|---------|
| #1 | GovernmentID | `did:web:identity.gov.example` | 180 days | Yes | No |
| #2 | BankAccount | `did:web:bank.bigfinance.example` | 90 days | Yes | No |

Each VC is a structured object with fields: `issuer`, `subject`, `credential_type`,
`days_since_issuance`, `is_revoked`, `issuer_is_trusted`.

The algorithm validates each VC:
- Skips revoked credentials
- Skips expired credentials (>3 years old)
- Verifies the subject matches the KERI AID (prevents using stolen VCs)
- Awards points for trusted issuers and credential type diversity

## Scoring Algorithm v2

Three pillars plus a synergy bonus:

| Pillar | Max Points | Factors |
|--------|-----------|---------|
| Cryptographic Identity (KERI) | 25 | AID age, witness count, key rotation |
| Verified Credentials | 45 | Valid VC count, trusted issuers, type diversity |
| Local Authentication | 20 | Biometric verification, peer endorsements |
| Cross-Pillar Synergy | 10 | Bonus if all 3 pillars have strong signals |

## Answers to Issue #6 Open Questions

1. **Do we actually need this?**
   **Yes.** Without verifiable execution, every peer must manually re-verify
   every credential of every interaction, defeating the purpose of an
   orchestrator agent. The PoC demonstrates that a single ZK proof replaces
   the need for Alice to parse Bob's raw credentials.

2. **Performance: Can a consumer laptop generate a ZK proof in a reasonable
   timeframe (under a few seconds)?**
   **Yes.** Proof generation takes ~5s on Apple Silicon for 2 VCs with
   structured string data. Verification is nearly instant (~18ms). This is
   acceptable for non-real-time identity assertions.

3. **Algorithm Identification: How do we standardize the algorithm Image IDs?**
   **Proposed:** A 3-level registry (see ALGORITHM_REGISTRY.md):
   - Level 1: Human-readable algorithm specification
   - Level 2: Reproducible build manifest (pinned toolchain → deterministic Image ID)
   - Level 3: Decentralized trust registry (KERI-anchored, versioned, auditable)

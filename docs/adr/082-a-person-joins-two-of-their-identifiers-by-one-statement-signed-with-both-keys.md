# ADR-082: A Person Joins Two of Their Identifiers to One Record by One Statement Signed With Both Keys

**Status:** Proposed (2026-11-15)
**Date:** 2026-11-15
**Deciders:** to be decided; the statement, the Ask and the routes below become public wire once this ships, and another party checks the statement
**Builds on:** ADR-045 (an asset has an identity and a grant), ADR-072 (a utility app is reached through its own back end), ADR-077 (a conversation's entries are checked by a bundle)

---

## Context

A person has a different identifier at every site they deal with, so that no two sites can tell they are the same person. That is the point of it, and it is also a cost. A site that has to keep something under one record for a person who reaches it by more than one identifier (a utility app that keeps notes about a person, where the person is known to the organisation by one identifier and signs in to the utility app by another) has no way to know they are the same person. Guessing from timing, or from an identifier the site never saw, is not a link. It has to be something the person says.

Saying it removes the unlinkability, toward that organisation, for those two identifiers. So the person has to be asked, and has to be shown what it does, and has to be the only one who can say it. Two failures have to be closed:

- Someone who holds only the **new** identifier must not be able to have it joined to a record that is not theirs: they would then read what is filed under that record.
- Someone who holds only the **record's** identifier must not be able to join another person's identifier to it for the same reason in reverse.

So the statement is signed by **both** keys, over the same bytes.

## Decision

1. **One statement, both keys.** The statement is JSON with these fields, in this order, no spaces: `v` (`BIND1`), `org` (the identifier of the organisation that asked), `site` (the site the new identifier is the person's at), `record` (an identifier the record already holds, or the one it starts from), `new` (the identifier being joined), `invite` (the digest of the single-use invite it answers, never the code) and `role` (`person`, or `owner` for the one who owns the organisation). Both the key of `record` and the key of `new` sign exactly those bytes. A link is the statement, the two keys and the two signatures. A key is written in the one spelling a key has: qb64, code `D`, canonical. A signature is qb64, code `0B`.
2. **What a checker refuses.** A link that is not signed by both keys; one in which the same signature stands for both; one whose bytes were changed after signing; one that joins an identifier to itself; one naming an organisation, site or invite other than the one the checker expects; one that omits a field; and one in which either key is not written in that spelling (plain base64, or another code, would let one key appear as two); one in which both identifiers have the same key, compared as the 32 bytes and not the strings, so one signature would stand for both; one in which any identifier or the invite is not written as an identifier is (letters, digits, `-` and `_`, 1 to 128 of them), which keeps the signed bytes plain ASCII so every implementation writes them alike; and one in which either key is not a current key of the identifier it is named for, read from that identifier's own key log (the key log travels with the statement, as it does with a sign-in: `login.KeyFromKeyLog`). The checker is told what to expect; the link never says what to expect.
   **What a checker must hold to be sure a key is current.** A key log that validates shows the key is a key of the identifier, and is the whole of what a sign-in shows today (`login.KeyFromKeyLog`): it does not show that the log is not cut off before a later rotation, and checks no witness receipts. A checker that must be sure compares the log with the one it holds for that identifier (a log shorter than its own is refused) or requires the witnesses' receipts on every event. This core does not rotate a relationship's identifier, so the person's Identity Agent sends the whole log it has, which is the inception; when relationships can rotate, the sign-in and this change to send the full log together. Relationship keys sign only bodies of a fixed form, this statement or an Ask, and never a string a caller chose.
3. **Any identifier already in the record may sign for it.** A person who has already joined an identifier to a record may later sign with that identifier, instead of the one the record started from, as `record`. The organisation accepts a link only if `record` is one of the identifiers its invite names, or is already joined (directly or through others) to one of them. Joining is read in either direction, so a record that was joined to another with both keys is one record.
4. **Two records of one person become one by the same statement.** Where `new` is already part of another record, the link is the person saying the two are one, and both keys signed it. Nothing else merges records.
5. **The invite is one more Ask type.** `t=7`, `bind_site` (5 stays reserved as `issue`, per ADR-021), minted by the organisation, carries the organisation, the site, the place the record's identifier is from (`record_site_aid`, with where its log is introduced), the role, the invite code and when the invite expires (`expiry`, the field every Ask may carry). **The Ask is signed by the organisation.** It carries `signer_oobi` (the pairwise key that signs every Ask) and `org_sig`: the organisation's own identity key, read from its key log at `org_oobi`, over a fixed form and not over the Ask's JSON. The form is `{"v":"ORGASK1","org":…,"site":…,"record_site":…,"role":…,"invite":…,"redeem_url":…,"org_name_sha256":…,"site_name_sha256":…}`: those fields in that order, JSON with no spaces. `org`, `site` and `record_site` are the Ask's `org_aid`, `site_aid` and `record_site_aid`; `invite` is the digest of the invite code (`invite_token`); `redeem_url` is the one address the organisation takes the statement at, plain ASCII with no query, whose path ends `/api/binding/invites/{invite_token}/redeem` (the person's Identity Agent also requires `https` unless its owner has allowed local sites); the two names are the SHA-256 of the Ask's `org_name` and `site_name` as UTF-8 bytes in lower-case hex, so what the person is shown cannot be changed by a host that relays the Ask, and a name with `&`, `<` or non-ASCII text signs the same bytes in every implementation. Every identifier is written as an identifier is. The version opens the bytes, so the identity key signs nothing else that looks like this. `binding-vectors.json` publishes invites (inputs, the organisation's key, the signed string, the signature) with one refusal per rule, and `check_binding_vectors.py` rebuilds them without Go. The person's Identity Agent refuses an Ask the organisation did not sign, and sends the statement and key logs only to `redeem_url`, never to the host that served the Ask: otherwise anybody could serve an Ask naming a real organisation and its real sites, or relay a genuine one, and collect a statement that proves two of the person's identifiers are one person to a party they never agreed to tell. **This protects only the first hand-off.** The statement and its two signatures are a proof anyone can check: once the organisation holds them it can show them to anyone, and nothing here stops it. What the person agrees to is that this organisation holds that proof, and the consent screen says so. An organisation whose identity key is not held where the invite is minted cannot mint one (the mint answers 409 and keeps nothing). **Both places must be the organisation's own identifier or a site it delegated**, read from the site's own log and the organisation's (the check a sign-in makes of a delegated site): otherwise an organisation could name any site the person holds an identifier at as the place the record is from, and the statement would hand it that identifier. A request naming a place that is not the organisation's is refused before the person is asked. The person's Identity Agent derives its identifier for the site, signs with that key and with the key it already holds for `record_site_aid`, and sends the link to `POST /api/binding/invites/{code}/redeem` on the organisation. It **never makes** an identifier for `record_site_aid`: one it does not hold is refused before the person is asked, and nothing is signed for it.
6. **The person approves.** The consent screen says what it does: that the organisation will know the person at the site and where they already deal with it are the same person, and that this cannot be undone except by leaving. "Not now" signs nothing and sends nothing, and the person's Identity Agent makes no identifier for the site.
7. **Single use, and nothing spent by a refusal.** The invite is redeemed once. It is reserved before the statement is read and handed back if the statement is refused, so a forged statement cannot use up an invite and a taken one cannot be taken twice. **An invite expires.** The organisation sets when it stops taking the statement (a week, or 1 to 720 hours as the owner asks), keeps that with the invite, and refuses a statement after it at redeem without spending the invite. The Ask carries the time as its `expiry`, which the person's Identity Agent checks for every Ask, so the person is not asked about an invite that has passed; it is not inside `org_sig`, because the organisation's own refusal is what holds. The person's Identity Agent keeps an identifier it made for the site only once the organisation has taken the statement: a refusal, or a statement that never arrived, leaves the person as they were. An invite is accepted only for its own purpose: an employment invite cannot be redeemed as a binding invite and the reverse, and an employment lookup does not describe a binding invite.
8. **The owner joins the same way, and a local owner cannot.** The owner's identifier is the one the organisation's identity settled on. The organisation mints an owner invite naming only that identifier, and checks again at redeem that it is still the owner. An organisation whose owner is not an identifier of its own that it holds a key log for (it is its own authority, which is the local case) **refuses to mint one**: it cannot assert an identifier it cannot check a key of. The owner, at the owner's own Identity Agent, approves on the same screen.
9. **What each side keeps.** The organisation keeps each joining (record, new, role, site, the signed bytes and both signatures), lists them to its owner (`GET /api/binding/links`), and exposes them to an extension in the same process (`Bindings`, `RecordOf`). The person's Identity Agent keeps, on the relationship the new identifier is, the organisation, the role, the identifier it joined to and when, and lists them to its owner (`GET /api/login/joined`), so a person can see every place they have said two identifiers are one.

## What this does not decide

Which organisations, sites and roles need a binding at all is a product's decision (a utility app's membership source decides it), not the protocol's. An employee whom the organisation already identifies by one identifier at every site it runs does not need one. What a site then keeps under the record is that site's. An owner's list of the binding invites still open, and withdrawing one before it is used or expires, is not decided here.

## Consequences

- New package `binding` (the statement, `Sign`, `Link.Verify`), its published vectors `binding/binding-vectors.json` (accepted and one refusal per rule), and an independent checker, `contracts/check_binding_vectors.py`, written from this text and not from the Go.
- `actions/registry.json` gains `bind_site` (7). `asset.EmployeeInvite` gains `Purpose`, `BindRole`, `RecordIdentifiers` and `ExpiresAt`; the store gains the joinings; `login.SiteRelationship` gains `Bound`.
- Four routes: `POST /api/binding/invites` (owner), `GET /api/binding/links` (owner), `POST /api/binding/invites/{code}/redeem` (open: the code is the credential, and what it takes is a statement only two keys can make), and `GET /api/login/joined` (owner) on a person's Identity Agent.
- A reader that knows only the earlier Ask types refuses `t=7`, as it refuses any type it does not know.
